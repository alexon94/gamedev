# Общие правила разработки игр и обучения

Эти правила действуют для всего репозитория и всех используемых движков. Дополняем и уточняем их по мере работы и по договорённости с пользователем.

Правила ниже применяются по умолчанию к новым игровым проектам: не нужно каждый раз заново согласовывать названия документов, их назначение и формат обучения. Конкретный запрос пользователя может изменить этот порядок.

## Общение и цель

- Общаться на русском языке, понятно и кратко.
- Помогать понимать код, устройство игры и процесс разработки; новые понятия и важные решения объяснять простыми словами, связывая их с поведением игры и причинами выбора.

## Рабочий процесс и объяснение изменений

- Изучать файлы и документацию перед изменениями, сохранять архитектуру проекта и не затрагивать посторонние файлы.
- Кратко объяснять действие и цель; для сложной задачи давать план.
- Самостоятельно реализовывать согласованный функциональный блок целиком, без остановок после каждой мелочи.
- После блока кратко перечислять затронутые файлы, их роли и связи; показывать ключевые новые или изменённые фрагменты кода.
- Пояснять, где выполняется фрагмент, какие данные использует и как влияет на игру. Для нового API объяснять назначение и важные аргументы.
- Соразмерять подробность сложности изменения: не ограничиваться «готово», но и не вставлять большие файлы целиком. Для правок документации показывать код не требуется.
- Давать время на разбор. Самостоятельную доработку предлагать только по желанию пользователя.

## Порядок создания игры

1. **Идея и границы.** Определить действие и цель игрока, платформу, технологию и небольшой MVP. Результат — понятная концепция и список обязательных возможностей в GDD; остальные идеи отложены.
2. **План и подготовка.** Разбить MVP на функциональные блоки с критериями готовности, подготовить документы и минимальный запускаемый проект. Результат — рабочий запуск и понятный первый блок реализации.
3. **Прототип.** На простой графике проверить основную механику и короткий цикл «начало → игра → завершение → повтор». Результат — играемая попытка; неудобную механику доработать до расширения.
4. **Реализация MVP.** Добавлять оставшиеся блоки плана: контент, интерфейс, сохранения, баланс, базовое оформление и звук по потребностям игры. Каждый блок проходит цикл ниже.
5. **Проверка MVP.** Проверить критерии GDD, стабильность, целевые устройства, баланс и игру без объяснений другим человеком. Результат — проверенная версия с явным списком оставшихся ограничений; непроверенные условия не считать выполненными.
6. **Улучшения и выпуск.** После MVP отдельно выбирать улучшения, например внешние спрайты; повторно проверять затронутые функции. Публикация — только по отдельному решению пользователя.

Цикл блока: выбрать объём и ожидаемый результат → реализовать → выполнить доступные проверки → объяснить изменения и дать ручной сценарий → исправить найденное → актуализировать проверенные пункты плана. Самостоятельные упражнения — по желанию; changelog — по запросу.

При продолжении существующего проекта сначала определить текущий этап и незакрытые критерии. Порядок адаптировать к жанру; по результатам тестов возвращаться к предыдущим этапам. Новые идеи не расширяют согласованный MVP автоматически.

## Новый проект и документы

- По идее, платформе и технологии определить небольшой MVP. Уточнять только недостающие важные решения.
- Создать отдельную папку проекта внутри направления технологии, не затрагивая другие игры.
- По умолчанию подготовить четыре документа под конкретную игру; существующие сначала прочитать, не перезаписывать шаблоном:
  - `README.md` — краткое описание, управление, запуск, зависимости и ссылки на документы. Без отчётов о разработке.
  - `GAME_DESIGN.md` в корне проекта — концепция, игровой цикл, правила, атмосфера, состав и критерии MVP (GDD). Будущие идеи — отдельным разделом внутри. Без архитектуры, API и технических настроек.
  - `TASKS.md` в корне проекта — крупные этапы реализации, чек-лист функций и условие готовности каждого. Без учебных заданий и инструкций настройки движка.
  - `CHANGELOG.md` — значимые выполненные изменения по датам: один раздел на день, новые сверху. Заполнять только по запросу; при создании достаточно заголовка и правила ведения.
- План конкретной игры составлять на основе общего порядка выше, адаптируя функциональные блоки к жанру и объёму.
- Внешнюю графику по умолчанию улучшать после MVP, если временной достаточно. Выпуск оставить отдельным этапом, выполняемым только по решению пользователя.
- Отмечать прогресс по подтверждённым проверкам, не закрывать непроверенные пункты или весь этап автоматически.
- Корневой README — универсальное описание репозитория без путей. Общие руководства хранить отдельно; дополнительные документы создавать только при необходимости или по запросу пользователя.

## Код и комментарии

- Писать простой, читаемый и поддерживаемый код с понятными именами.
- Предпочитать существующие решения, избегать преждевременных абстракций и лишних зависимостей.
- Обрабатывать необходимые ошибки и пограничные случаи.
- В начале файла кода кратко описывать по-русски его назначение и ответственность; поддерживать описание актуальным. Использовать синтаксис комментариев соответствующего языка.
- Перед смысловыми блоками объяснять, что они делают и зачем: подготовка попытки, ввод, движение, столкновения, счёт, завершение и очистка.
- При первом использовании незнакомого API или приёма кратко пояснять его смысл, важные аргументы или единицы измерения. Не повторять одинаковые пояснения при каждом вызове.
- Не комментировать каждую строку и очевидные операции. Комментарии должны помогать понимать логику, а не пересказывать синтаксис.

## Проверка и итог

- Выполнять уместные проверки синтаксиса и тесты логики после изменений, когда это возможно. Полную сборку или экспорт запускать по запросу или отдельно согласованной необходимости.
- Честно сообщать, что проверено, что осталось проверить и какие проблемы найдены; отдельно указывать предстоящие ручные проверки пользователя.
- Не выдавать успешную сборку или проверку синтаксиса за проверку поведения в игре.
- После каждого законченного блока реализации давать короткий нумерованный сценарий ручного тестирования: что открыть или нажать и какой результат ожидается. Включать новые функции и связанные с ними важные проверки, например повтор, паузу или сохранение.
- Пользователь проверяет поведение через dev-сервер или в игровом движке. Учитывать подтверждённые результаты и не просить повторять тот же сценарий без причины.

## Сохранность и Git

- Сохранять существующие изменения пользователя.
- Не добавлять пароли, токены и другие секреты в код.
- Не выполнять разрушительные команды и не удалять важные данные без явного разрешения.
- Не менять настройки production без разрешения.
- Не создавать коммиты, не отправлять изменения и не выполнять публикацию или развёртывание без запроса пользователя.
