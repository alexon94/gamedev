# Разработка 2D-игры на Phaser

Общее руководство: от выбора инструментов и прототипа до сцен, ресурсов, проверки и выпуска браузерной игры.

GDD конкретной игры описывает замысел и правила. Plan определяет этапы и технические решения проекта. Этот гайд объясняет работу с Phaser и может использоваться для разных игр.

## Что такое Phaser и с чего начать

Phaser — фреймворк для браузерных 2D-игр на JavaScript и TypeScript. Логику и состав экранов задают кодом, а графику и карты можно готовить во внешних редакторах. В Godot для сборки игры есть встроенный визуальный редактор сцен и узлов. В этом руководстве используем JavaScript.

Порядок работы: идея и границы MVP → подготовка → прототип → полный короткий игровой цикл → наполнение → баланс и оформление → проверка → выпуск. После проверок можно возвращаться к предыдущим этапам. Сначала достаточно одной работающей попытки или комнаты.

## 1. Подготовить окружение

Для описанного процесса нужны редактор кода, браузер с инструментами разработчика, Node.js с npm и Git. Используем JavaScript с модулями и Vite для локального сервера и сборки. До установки проверяем требования выбранной версии Vite к Node.js в [официальном руководстве](https://vite.dev/guide/).

Выбираем совместимые версии инструментов и Phaser, фиксируем зависимости и lock-файл. Не обновляем движок посреди этапа без причины. Установку выполняем в каталоге конкретной игры, а не в корне репозитория с несколькими проектами.

Дополнительные инструменты подключаем по необходимости:

| Задача | Инструменты |
|---|---|
| Пиксель-арт и кадры анимации | Aseprite, LibreSprite |
| Рисованные фоны и персонажи | Krita |
| Векторная графика | Inkscape |
| Карты и размещение объектов | Tiled |
| Обработка звука | Audacity |
| Создание музыки | LMMS |
| Рендеры 3D-объектов в 2D-спрайты | Blender, если этого требует стиль |

Для первого прототипа отдельные графические редакторы необязательны.

## 2. Подготовить структуру и запуск

```text
game/
├── index.html
├── package.json
├── package-lock.json
├── public/assets/
├── src/
│   ├── main.js
│   ├── settings.js
│   └── scenes/
├── GDD.md
└── Plan.md
```

Это начальная схема, а не обязательный стандарт. Папки объектов, карт и сервисов добавляем по необходимости. В `main.js` создаём игру и регистрируем сцены, в `settings.js` держим параметры настройки.

В `package.json` определяем команды `dev` → `vite`, `build` → `vite build`, `preview` → `vite preview`. После установки зависимостей запускаем `npm run dev` и открываем адрес, который выдал сервер. HTML двойным щелчком не запускаем: ресурсы и модули проверяем через HTTP.

Проверка: страница открывается; в Console нет ошибок, в Network нет отсутствующих ресурсов. Эти команды предполагают уже настроенный проект — сами по себе они его не создают.

## 3. Организовать сцены

Сцена объединяет логику отдельного экрана. Обычно достаточно меню, игры и результатов. Методы жизненного цикла включают `init()` для начальных данных, `preload()` для загрузки, `create()` для создания объектов и `update(time, delta)` для покадровой логики. Подробности — в [руководстве по сценам](https://docs.phaser.io/phaser/concepts/scenes).

Обработчики ввода не регистрируем каждый кадр. При остановке сцены освобождаем собственные внешние подписки; при повторном запуске заново инициализируем состояние попытки. Для множества похожих уровней используем данные уровней и общую игровую сцену, если отдельные классы не нужны.

## 4. Создать прототип и управление

Начинаем с геометрических фигур или временных текстур. Сначала проверяем положение, движение и управление, затем добавляем оформление. Клавиатуру и указатель подключаем через систему ввода Phaser. Состояние удержания сбрасываем при потере фокуса.

`delta` в `update` задаётся в миллисекундах. При ручном перемещении со скоростью в пикселях в секунду используем секунды: `distance = speed * delta / 1000`. Если положение обновляет физический движок, не прибавляем тот же путь вручную: иначе движение будет рассчитано дважды.

## 5. Настроить физику и столкновения

Для простой аркады рассматриваем Arcade Physics. Подключаем её в конфигурации игры, создаём физические тела и включаем отладочное отображение. Изображение и тело могут иметь разные размеры; проверяем их центры и смещения. Пример подключения есть в [официальном первом уроке](https://docs.phaser.io/phaser/getting-started/making-your-first-phaser-game).

Для физического взаимодействия используем collider, для обнаружения пересечения без раздвигания — overlap. Награды и поражение защищаем от повторного срабатывания. Объекты вне игровой области удаляем или возвращаем в пул, если он действительно нужен.

## 6. Добавить ресурсы и контент

Временную графику постепенно заменяем изображениями, загружаемыми по ключам. При выбранной структуре Vite файлы из `public/assets/` доступны по пути `assets/…` с учётом размещения сайта. Проверяем пути и регистр имён в собранной версии.

Покадровые анимации подходят для персонажа; tweens — для изменения прозрачности, масштаба и интерфейса. Tiled и карты JSON подключаем, если игра требует карт: для бесконечной аркады они необязательны. Ресурсы должны иметь подходящие лицензии.

### Персонаж и эффекты

Последовательность работы: временное изображение → создание объекта → ввод и движение → столкновения → анимации. Повторяющуюся между уровнями логику игрока выделяем в переиспользуемый объект. Частицы подходят для искр и вспышек, эффекты камеры — для обратной связи; они не должны скрывать опасности.

### Уровни

Один фиксированный маршрут можно задать прямо в прототипе. Для нескольких уровней удобно отделить данные от логики. Например, собственная схема комнаты может хранить координаты игрока, выхода, стен и ловушек в JSON. Код проекта определяет единицы координат и размеры объектов. Для карт по сетке и визуального размещения можно подключить Tiled и согласовать экспорт с загрузчиком игры.

Для учебной игры с комнатами сначала соберите одну: игрок, стена, ловушка, выход и повтор. Следующие комнаты вводят испытания постепенно: показать механику → дать потренироваться → соединить с другой → проверить навык. Не нужно сразу создавать десятки уровней.

## 7. Проверить интерфейс, звук и сохранения

Разделяем логический размер игры и размер окна. Проверяем масштаб, пропорции и читаемость текста. Звук запускаем после взаимодействия пользователя и даём возможность отключить его.

Для небольшого локального прогресса можно использовать браузерное хранилище. Проверяем загруженные значения, обрабатываем ошибки чтения и записи. При недоступном сохранении игра должна продолжать работать. Данные другого браузера или адреса сайта не считаем автоматически общими.

## 8. Отладить и подготовить сборку

Проверяем Console, Network, хитбоксы, повторные запуски сцен, паузу и число активных объектов. Сначала устраняем воспроизводимые ошибки; оптимизируем после измерения проблемы.

В настроенном проекте выполняем `npm run build`, затем `npm run preview` и проверяем собранную игру. Preview предназначен для локальной проверки, а не для постоянного хостинга. Перед размещением в подпапке проверяем базовый путь ресурсов. Подробнее — [размещение сборки Vite](https://vite.dev/guide/static-deploy).

Публикация выполняется отдельно после проверки версии и выбора площадки. После размещения повторно проверяем запуск, ресурсы, звук и сохранение по конечному адресу.

### Проверка на устройствах

Проверяем понятность управления без объяснений, точность столкновений, скорость повтора, сохранения и читаемость на разных экранах. Если телефоны входят в целевые устройства, отдельно проверяем мобильный браузер, касания, ориентацию и производительность. Исправность настольной версии этого не гарантирует.

### Размещение и Android

Браузерная сборка состоит из статических файлов и ресурсов. Для игровых площадок отдельно проверяем требования к размещению и интеграциям.

Android-версию можно рассматривать как отдельный этап: веб-игру упаковывают через WebView, например с помощью Capacitor. Это требует собственной проверки сборки, сенсорного управления, звука и производительности. Такая упаковка не входит автоматически в готовность браузерной версии.
